Scope and uncertainty: Reviewed only the two supplied excerpts at commit bfdfaa49120a6aaf5dc2e1d6e467ee48090d6ac7. Both are marked untruncated; their completeness was not independently verified. Callers, deployment configuration, filesystem protections, and downstream consumers were not supplied. Findings describe potential risks, not demonstrated exploits or measured outcomes.

1. Approval binding: collectHandoff uses workflow_dispatch validation, which checks current permissions and the current run label but does not establish who applied that label or bind approval to a particular body revision. An edited issue can retain its label and produce a new validated revision. Before any future execution, require explicit approval bound to repository, issue, revision, and action, with revalidation immediately before use.

2. Replay scope and durability: The ledger retains previously seen keys and preserves history on rejection, which supports local duplicate detection. Protection depends on the same intact state directory; deleting or replacing it, or using another machine, permits a fresh receipt. The file is synchronized before rename, but the containing directory is not synchronized afterward, leaving crash durability uncertain. A duplicate is returned as a flag rather than blocked, so downstream handling matters. Do not treat this ledger as proof of exactly-once execution.

3. Filesystem races: withLock does not verify the state directory before creating its lock. storeReceipt checks the final directory and ledger with lstat, but later reads and renames use paths, permitting replacement races if another local actor can modify the directory or its ancestors. Ancestor symlinks and existing directory permissions are not checked. Review ownership and permissions and use directory-bound file operations where supported. Abrupt termination can also leave a stale lock requiring controlled recovery.

4. Process trust: Shell-free spawning and bounded timeouts/output reduce command injection and resource risks. However, gh and the optional codex version probe resolve executables through the process environment. A compromised executable search path or configuration could run unintended code. Review executable provenance and environment controls. The version probe is not called by main in the excerpt.

5. Execution boundary: The validator always returns executionAllowed false, and main blocks when autonomous execution is enabled. No task execution or remote write path is visible. These are useful present safeguards, but validated status and receipt flags are metadata rather than enforcement for an unseen consumer. Exported helpers also bypass main's environment checks when called directly; they still do not execute tasks in the supplied code.

Human review disposition: Preserve report-only behavior. Resolve revision-bound approval and define durable replay enforcement before connecting these receipts to execution. Overall safety remains uncertain without the surrounding integration and deployment context.

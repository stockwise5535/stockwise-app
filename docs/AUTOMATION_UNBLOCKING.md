## CRM hardening (SQL proposal only)

Updated `docs/proposals/APAC_GROWTH_CRM.sql` remains outside registered migrations:

- RPCs bind auth.uid() to existing Growth Admin AND workspace owner/admin; no browser table DML, anonymous execute or owner→internal-admin escalation.
- Payload hash is computed by PostgreSQL from jsonb canonical text (SHA-256); it is a DB-specific approval hash, not interchangeable with the fixture JS/Buffer/Gmail hashes. Edits increment version and return to draft; claimed/uncertain payloads cannot be edited. DB clients must read returned version/hash, never guess them.
- Approval trigger binds current item/version/hash and exact authenticated actor; approvals/activity reject UPDATE/DELETE. Repeated approval reuses its version and idempotent audit source ID. Privileged database owners can still alter/drop triggers; this is not tamper-proof against administrators and service-role access must remain restricted.
- Claim RPC locks workspace using transaction-scoped advisory lock, locks target row, checks exact approved version/hash, atomically reserves unique kind+content identity, changes state and appends audit. Quotas are serialized at 10/hour, 50/day per workspace; failed/unknown reservations consume capacity conservatively. Claim only reserves; it does not authorize external sending or replace Gmail's stricter gates/global quotas/consent. A sending/unknown item is never automatically reclaimable. No provider worker is connected to these RPCs.
- Local tests cover ordinary owner/anonymous/foreign workspace denial, forged actor/hash rejection, edit invalidation, audit immutability, duplicate claim/content rejection, quota exhaustion and rollback. PGlite queues simultaneous requests; Promise.allSettled duplicate checks are **not** proof of distributed PostgreSQL multi-connection races. Advisory locking still needs two-connection hosted/disposable rehearsal before live use.
- Remaining blockers: company/contact/population CRUD with normalized/allowlisted PII; retention/withdrawal legal policy; transactional suppression reconciliation, provider result/unknown reconciliation, actual worker integration and distributed load/race tests. These changes resolve identified approval/audit/reservation defects, not the entire production CRM.
